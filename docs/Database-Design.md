# Vidyareel V1: Database Design

*Owner: adit · Draft 2 (checked line by line against the System Design doc) · 21 Oct 2026 · Based on PRD draft 3, the System Design doc (sections 4 and 6) and the local prototype. Database: MongoDB Atlas (free M0). Files live in Cloudflare R2, never in the database.*

## 1. Assumptions (change any of these and tell me)

1. **Mongoose** is the ORM for all collections (PRD section 9), including the auth collections `users`, `sessions` and `password_resets`, which the app owns (no auth library).
2. **System Design section 11.4 decisions stand**: whole-timeline render for scene fixes, daily limit counted at creation and refunded on a failed render, time zone defaults to Asia/Kolkata and is stored per member, stock voices only until the voice decision is made.
3. Ids are MongoDB `ObjectId` in the database and 24-character hex strings in the API. Scene ids are short strings (`sc_` + 8 random characters) generated by the app, so scenes can be reordered without renumbering.
4. All times are stored in UTC as BSON dates. Durations are in milliseconds (`...Ms`) or whole seconds (`...Sec`), named as such. The time zone only matters for the daily limit and for showing times in the UI.
5. Voices and music tracks are a small fixed list kept in config (`src/config/voices.ts`, `src/config/music.ts`), not collections. The voice list holds only voices that passed the one-time ElevenLabs probe (System Design 7.2); voice samples are pre-generated once into R2 (section 5).
6. One member can own several videos, one Instagram connection (V1: one active connection per member), and many posts.
7. No billing data exists anywhere. `usage_log` records quota usage only.
8. Instagram tokens are encrypted with AES-256-GCM using a key in a Vercel environment variable. The database never holds the key.
9. Soft delete uses `deletedAt`. Every query on `videos` filters `deletedAt: null` unless it is the cleanup job.

## 3. Relations

```
user 1──1 approved_emails          (joined by lowercased email)
user 1──* videos
user 1──0..1 instagram_connections
videos 1──* render_jobs            (only one active at a time)
videos 1──* posts
videos 1──* assets                 (also via scenes[].media.assetId)
instagram_connections 1──* posts
user 1──* usage_log, notifications
videos 1──* usage_log              (optional videoId)
```

Relations are by id reference, checked in the service layer (MongoDB does not enforce foreign keys). Scenes, elements, word timings and the chosen media for each scene are **embedded** in the video, because the Review screen, the player and the render all need them together and a 90 second video is only about 12 scenes.

## 4. Collection details

Notation: `type`, `?` means optional, `[]` is an array. "Unique" and index details are in section 6.

### 4.1 Auth collections (`users`, `sessions`, `password_resets`)

Owned by the app (`src/server/auth`).

**`users`:** `email` (lowercased, unique), `name`, `passwordHash?` (scrypt, salted; absent for Google-only accounts), `googleId?` (unique, sparse), `emailVerifiedAt?` (set for Google accounts), `timeZone`, `createdAt`, `updatedAt`. An account may have a password, a Google id, or both (Google sign-in with an existing email links to that user).

**`sessions`:** `userId`, `tokenHash` (SHA-256 of the random cookie token; the raw token is never stored), `expiresAt` (7 days, extended on use), `userAgent`, `createdAt`. Index on `tokenHash` (unique) and `userId`; TTL on `expiresAt`.

**`password_resets`:** `userId`, `tokenHash`, `expiresAt` (30 minutes), `usedAt?`. TTL on `expiresAt`. A new request invalidates earlier unused tokens; using one deletes all of the user's `sessions`.

`oauth_states` is shared with Instagram connect and gains `purpose: "google" | "instagram"` plus the PKCE `codeVerifier` for Google.

**Role is deliberately not copied onto `users`**: it is read from `approved_emails` on every request (System Design section 9), so it cannot drift:

| Field | Type | Notes |
| --- | --- | --- |
| `timeZone` | string | IANA zone, default `Asia/Kolkata`. Used for the daily limit day boundary and for showing scheduled times. |

Sign-up gate (in the `signup` service and the Google callback): the lowercased email must exist in `approved_emails` and not be removed, otherwise the service throws `INVITE_ONLY` and no `users` document is written (this applies to Google sign-up too). The first admin: when the email equals `ADMIN_EMAIL` and `approved_emails` is empty, the hook inserts the row with role `admin` before allowing sign-up (System Design 3.1).

#### 4.3.1 Scene (embedded in `videos.scenes`)

Aligned with the prototype's `SceneProps` and the sync section of the PRD.

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | `sc_xxxxxxxx`. Stable across reorder. |
| `order` | int | 0-based. Re-numbered on reorder or delete. |
| `template` | enum | `title-hook`, `bullet-reveal`, `step-flow`, `definition-callout`, `diagram` in the prototype; the PRD library adds `comparison`, `stat`, `timeline`, `formula`, `stock-clip`, `recap`. |
| `diagram` | string? | Only when `template = diagram`: `raindrop`, `orbit`, `flow`, and later others. |
| `title` | string? | Scene heading on screen. |
| `narration` | string | Spoken text. |
| `onScreenText` | string[] | Text lines shown (derived from elements for most templates; stored for edit). |
| `needsCheck` | bool | "Check this" marker (S8) for numbers, dates and claims. |
| `elements` | Element[] | `{ id, type, text, cue, startMs? }`. In **spoken order** (the storyboard rule). `startMs` is filled by sync. See the timing note below. |
| `audio` | object? | `{ hash, key, durationMs, words: [{ word, startMs, endMs }] }`. `hash` = hash of narration + voiceId + speed; if unchanged, voice is not regenerated. `key` is the R2 key of the mp3. `durationMs` = last word end + 50 ms (System Design 7.2). Word times are scene-local, **without** the lead-in. |
| `durationMs` | int? | Scene length set by sync: lead-in 150 ms + audio duration + tail 150 ms (the PRD's 0.3 s pause; System Design 7.3). |
| `needsAttention` | bool | Set when an automatic sync quality check fails and could not be fixed automatically (System Design 7.3). Shown to the member as a warning on Review. |
| `media` | object? | For stock-clip scenes: `{ assetId, query, resultIndex }`. `resultIndex` supports "Try another". |
| `syncWarnings` | string[] | e.g. "cue not found, spaced evenly", "elements sorted". Not shown to users in V1; useful in the Admin usage view and debugging. |
| `notes` | string? | Reserved. |

**Timing note.** System Design stores sync output in milliseconds in the database (render step table) but works in frames inside the Remotion props. This design stores **milliseconds** in MongoDB and converts when building props: `startFrame = round((leadInMs + startMs) / 1000 * 30) - 3`, i.e. the visual lands 3 frames before the spoken word (7.3). The first element of a scene is clamped to within 4 frames of the scene start.

Sizing check: 12 scenes × (300 words of narration + word timings of about 40 words × 40 bytes) is under 100 KB, far below the 16 MB limit.

### 4.8 `usage_log`

Append-only. Used for the quota guards and the Admin usage view.

| Field | Type | Notes |
| --- | --- | --- |
| `userId` | ObjectId | |
| `videoId` | ObjectId? | |
| `type` | enum | `video_created`, `llm`, `voice_credits`, `render_sec` (System Design) plus `video_refund` (the compensating row it describes). |
| `units` | number | `video_created` = 1, `video_refund` = -1, `voice_credits` = estimated credits, `render_sec` = seconds, `llm` = 1 call. |
| `provider` | string? | e.g. `gemini`, `elevenlabs`. |
| `meta` | object? | Free-form (model id, scene count). |

Counting rules:
- **Videos used today** = sum of `units` where `type in (video_created, video_refund)` for the member within their local day (computed from `user.timeZone`).
- **Voice credits used this month** = sum of `voice_credits` for the **calendar month** (System Design 7.2), UTC. The budget is the env var `ELEVENLABS_MONTHLY_CREDITS`. The app does not read quota from ElevenLabs (the testing key had no `user_read` scope), so `usage_log` is the only source. Rows carry estimated credits (about one per narration character) written when voice is generated.
- A **fix a scene** writes no `video_created` row. A failed **or cancelled** render writes one `video_refund` row (System Design runs `onFailure` for cancels too; compensating entry, so the log stays append-only). A storyboard that cannot be generated is also refunded.

## 7. State machines and write rules

### 7.1 Status transitions

| Entity | Transitions |
| --- | --- |
| `videos.status` | `draft` → `storyboard_ready` → `rendering` → `ready`. `rendering` → `failed` (Try again returns to `rendering`). `ready` → `scheduled` → `posted`. Posting immediately goes `ready` → `posted`. Editing a ready video reopens `storyboard_ready`; the previous `outputKey` is cleared only after the new render succeeds. `posted` is terminal for the status, but the member can still start a fresh post of the same video after a warning (PRD edge case). |
| `render_jobs.status` | `queued` → `running` → `succeeded \| failed \| cancelled` |
| `posts.status` | `scheduled` → `publishing` → `posted \| failed`; `scheduled` → `cancelled`; `failed` → `publishing` on retry |
| `instagram_connections.status` | `connected` ↔ `needs_reconnect`; Disconnect deletes the document. Entering `needs_reconnect` sets `posts.paused` on that member's live posts; returning to `connected` clears it |

Transitions are done with a conditional update (`updateOne({ _id, status: <expected> }, ...)`), so two requests cannot both move a video forward.

### 7.2 Consistency rules

- **Optimistic concurrency** on `videos`: autosave sends `version`; the update filter includes it and does `$inc: { version: 1 }`. Mismatch returns `VERSION_CONFLICT` (409) and the UI reloads. Workflow writes (progress, scene audio) use scene-level positional updates (`scenes.$[s].audio`) and do **not** require `version`, but they do bump it, so an open editor sees a conflict instead of overwriting server-written audio.
- **Idempotency:** workflow steps upsert keyed by `(videoId, sceneId, audio.hash)` or `postId`. Running a step twice never duplicates a render or a post. Request-level idempotency uses `idempotency_keys`.
- **Locking:** the storyboard is locked (scene edits rejected with `VIDEO_LOCKED`) while `status = rendering`.
- **Transactions:** MongoDB Atlas M0 supports multi-document transactions on replica sets. Use one only where two collections must change together: creating a video together with its `video_created` row. Everything else is single-document or idempotent.
- **Quota counting:** daily cap checked and the `video_created` row written in the same transaction as the video insert, so two simultaneous requests cannot slip past the limit.

## 8. Retention and deletion

Only the first row (7-day grace for deleted videos) is fixed by the PRD (L6) and System Design. The other periods are **proposed defaults** from this doc and can be changed.

| Data | Kept for | Then |
| --- | --- | --- |
| Deleted video (`deletedAt` set) | 7 days | `cleanupDeletedVideos` (daily) deletes its R2 objects (audio, props, out, thumb), `render_jobs`, `posts` (not the Instagram post itself), `assets` rows, then the video document. |
| Cancelled or failed render files | 7 days after the job finishes | Cleanup deletes partial R2 objects. |
| `render_jobs` | 90 days | Deleted by cleanup (the video keeps `currentJobId` nulled). |
| `posts` (posted, cancelled) | Life of the video | Deleted with it. |
| `usage_log` | 13 months | Monthly cleanup. Needed only for the current month and day; older rows are for the Admin trends view. |
| `notifications` | 90 days | TTL index. |
| `oauth_states` | 10 minutes | TTL index. |
| `idempotency_keys` | 24 hours | TTL index. |
| `rate_limits` | 1 to 2 minutes | TTL index. |
| `sessions` | 7 days, extended on use | TTL index on `expiresAt`. |
| `password_resets` | 30 minutes | TTL index on `expiresAt`. |
| Removed member (`approved_emails.removedAt`) | Row 30 days; videos kept until an admin chooses delete | "Delete their data" soft-deletes all their videos (7-day grace), hard-deletes `instagram_connections` and `notifications`, and deletes their `usage_log` rows (V1 logs are quota data only, so they are removed with the member). |
| Instagram token | While connected | Deleted on Disconnect, on member removal, or after 30 days in `needs_reconnect` with no action. |
| Stock clip cache (`media/…`) | Until no `assets` row references it for 30 days | Weekly sweep (optional, P2). |

Delete my data (A8, P1) = the member-removal data deletion above, triggered by the member for themselves.

## 9. Security notes for the database

- Atlas user for the app has `readWrite` on the one database only. IP access: Vercel does not have fixed IPs, so Atlas network access is `0.0.0.0/0` with a strong password and TLS, unless Vercel Secure Compute/ static IPs are enabled (check). Note this as an accepted risk for an internal project.
- No secrets in documents, except the encrypted Instagram token. Inngest step results contain only ids and keys.
- Every query for member-owned data includes `userId` in the filter (`videos`, `posts`, `render_jobs`, `notifications`). The service layer exposes only functions that take `userId`; there is no "find by id only" helper outside admin and workflow code.
- Backups: M0 has no automatic backups and System Design lists a scheduled export as the mitigation. Decision: a weekly Inngest cron `exportBackup` writes JSON exports of `approved_emails`, `videos`, `posts` and `instagram_connections` (token fields stay encrypted) to a separate private R2 prefix `backups/`, keeping the last 4. Add it in Phase 6 (hardening).

## 10. Migrations and seed data

- Mongoose schemas carry a `schemaVersion` on `videos` (start at 1). When a template or field changes, a lazy migration function upgrades documents on read; no bulk migration framework for V1.
- Indexes are created by a `scripts/ensure-indexes.ts` script run on deploy (Mongoose `autoIndex` off in production so a deploy cannot lock a collection).
- Seed: `ADMIN_EMAIL` row in `approved_emails`; voices and music from config; no sample data.

## 11. Decisions on the earlier open items

| Open item | Decision |
| --- | --- |
| When ElevenLabs credits reset | Use the calendar month (System Design 7.2), budget from `ELEVENLABS_MONTHLY_CREDITS`. If the real reset day differs, change the window in one function (`monthWindow()`); no schema change. |
| Creator accounts publishing | Schema-neutral: `accountType` stores whatever Meta returns. Default allowed set is `BUSINESS` only (the confirmed case); `IG_ALLOWED_ACCOUNT_TYPES` env var adds `CREATOR` after a Phase 0 test. |
| Atlas network access | Vercel has no fixed IPs on Hobby, so allow `0.0.0.0/0` with a dedicated least-privilege user, a long random password and TLS. Accepted risk for an internal tool; revisit if static IPs become available. |
| Theme names and music ids | `theme` and `musicId` are plain strings validated against config, so the final names can change without a migration. |
